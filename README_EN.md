# Slack → Multica Relay

**English** | [简体中文](README.md)

A reliability-focused Slack → Multica bridge. It accepts signed Slack mentions, persists them through QStash, maps each Slack thread to a Multica Issue, and delivers later mentions as comments to the same Agent workflow.

## Why this project exists

A direct Slack-to-Agent integration easily conflates “Slack acknowledged the event,” “the task was persisted,” “the Agent completed,” and “the reply reached the user.” This project separates those stages and gives admission, retries, context, idempotency, and final delivery explicit owners:

- Slack receives success only after QStash accepts the event.
- The queue consumer applies the same admission policy again.
- Redis stores thread mappings, frozen event snapshots, and Multica write state.
- Stable markers reconcile Multica Issue/comment writes whose result is unknown.
- A durable local delivery ledger prevents the reply adapter from blindly repeating an uncertain Slack send.

## Highlights

- **Strict admission** — validates Slack signatures and timestamps, with Team, mention target, channel, and sender allowlists/blocklists.
- **Durable ingestion** — uses QStash to separate Slack's short response window from context collection and Multica writes.
- **Thread → Issue routing** — creates one Issue for the first accepted mention in a Slack thread and appends later mentions as comments.
- **Bounded nearby discussion** — the first mention includes 12 roots from the preceding 30 minutes and expands 2 recently active threads with 5 replies each.
- **Complete follow-up intervals** — retain root, previous persisted mention, and every intervening message, plus initial nearby background; one message per line, with no delta merge.
- **Explicit missing-context boundaries** — optional gaps are marked; incomplete or oversized required conversation rejects dispatch instead of being silently truncated.
- **Privacy minimization** — Slack file objects are projected before QStash; private URLs, thumbnails, shares, downloaded content, and credentials never enter the queue payload.
- **Deterministic footer** — the display identity, configured model, and Fast label are rendered by code rather than generated by the model.
- **Thread cancellation** — target users can cancel associated runs with a mention plus cancel/取消; run targets and reaction cleanup are persisted.
- **Final-reply context** — parallel Skill statistics, Multica task links, and GitHub PR/branch associations, with private style and emoji configuration.
- **Final-send deduplication** — every source Issue/comment gets a stable delivery block ID and a local `attempting → accepted → sent` ledger.
- **Three deployment adapters** — the shared implementation can run behind Vercel Functions, EdgeOne Cloud Functions, or Cloudflare Workers.

## How it works

```text
Slack mention
  │
  ├─ signature, timestamp, and admission checks
  ▼
QStash
  │  durable delivery, per-thread serialization, bounded retries
  ▼
Queue consumer
  ├─ admission policy recheck
  ├─ cancellation: fixed run targets, terminal readback, own reaction cleanup
  ├─ Redis and marker recovery of thread, event, and persisted mention boundary
  ├─ ordinary request: complete thread interval, initial background, and explicit links
  └─ Multica Issue creation or comment append
       │
       ▼
Configured Multica Agent
       │
       └─ local scripts/slack-reply.py
            ├─ read back the source envelope
            ├─ render body blocks and footer
            ├─ persist the delivery ledger
            └─ reply in the original Slack thread
```

The Relay deployment and the Agent Runtime are separate trust domains. Vercel, EdgeOne, or Cloudflare Workers owns ingress, queue consumption, and Multica routing. Private Agent Instructions, Skills, the Slack user token, and reply-adapter configuration stay on the Runtime that executes the Agent.

## Context model

Each new mention produces a frozen v5 envelope. First mentions include the complete current thread and bounded nearby discussion. Follow-ups retain all same-thread conversation since the previous persisted mention and preserve initial background. Messages use compact single-line JSON with empty defaults omitted. Incomplete mandatory pagination or size overflow rejects dispatch instead of silently dropping conversation; optional gaps are marked separately. Retries reuse frozen input.

See [Slack Context Assembly](docs/CONTEXT-ASSEMBLY-DESIGN_EN.md) for the complete data shape, exact limits, pagination rules, and failure semantics.

The Relay code owns this policy; no new environment variables or Agent personality changes are needed. New mentions use v5 after deployment. Frozen snapshots are reused while their 24-hour cache is valid, and historical Issues/comments remain unchanged. Late requests retain the original background timestamp and exclude future background roots/replies. Failed recovery retries or rejects instead of assuming no previous mention. See [Multica Operations](docs/MULTICA-OPERATIONS_EN.md) for readback and error classification.

Agent messages with an explicit Relay marker and recognized adapter layout retain their block body without footer metadata, marked footerOmitted. Unrecognized layouts keep original text. Model snapshots use workerd-compatible requests that do not follow redirects.

## Reliability semantics

The project keeps these states separate:

1. The Slack event passed admission.
2. QStash accepted the event.
3. The Multica Issue/comment was persisted.
4. The Agent ran.
5. The final Slack reply was delivered.

An HTTP 200, acknowledgement reaction, created Issue, or ready deployment proves only its own stage.

Multica writes use Redis state and stable markers for retry recovery. Final Slack replies use a durable local ledger. A verified `sent` result is reused directly. If a POST result is unknown, the adapter reads the original thread; an empty read does not authorize another POST. It returns `slack_delivery_unknown` for independent verification instead, prioritizing duplicate prevention.

## Prerequisites

To deploy the Relay, you need:

- Node.js 22.12+ (Node.js 24 LTS recommended) and pnpm 10;
- a Slack App configured for the Events API;
- QStash;
- a dedicated Upstash Redis database;
- a Multica PAT that can access the target Workspace, Project, and Agent;
- a Vercel, EdgeOne, or Cloudflare Workers deployment environment.

To reply through the local adapter with a selected user identity, you also need:

- Python 3;
- an authenticated Multica CLI;
- a local Multica Runtime bound to the target Agent;
- a `SLACK_USER_TOKEN` with `chat:write` and the history scope for the selected conversation type.

The repository defaults to Node.js 24 via `.nvmrc` and `.node-version`; Node.js 22.12+ remains supported. Select Node.js 24 for hosted builds. Cloudflare Workers executes on workerd, independently of the Node.js build version.

## Local installation and validation

```bash
git clone https://github.com/Perfecto23/slack-multica-relay.git
cd slack-multica-relay
pnpm install --frozen-lockfile
pnpm test
pnpm lint
```

`.env.example` lists every Relay deployment variable. For deployment or local integration work, provide the required values through the target platform or a private environment. Never commit `.env.local`, prompts, persona material, private deployment records, or credentials.

See [Configuration](docs/CONFIGURATION_EN.md) for variable sources, Runtime configuration, and deployment verification.

## Deployment entry points

| Platform | Slack Events | Queue consumer | Health |
| --- | --- | --- | --- |
| Vercel | `/api/slack/events` | `/api/queue/consume` | `/api/health` |
| EdgeOne | `/api/slack/events` | `/api/queue/consume` | `/api/health` |
| Cloudflare Workers | `/api/slack/events` | `/api/queue/consume` | `/api/health` |

### Vercel / EdgeOne

1. Import this repository into Vercel or EdgeOne. Platform settings live in `vercel.json` and `edgeone.json`.
2. Create the Relay environment from [Configuration](docs/CONFIGURATION_EN.md), placing tokens, PATs, and signing keys in the platform secret store.
3. After the public domain is known, set `RELAY_CONSUMER_URL` to its exact `/api/queue/consume` URL. It must match the URL used by QStash for delivery and signature verification.
4. Deploy the immutable commit that passed validation, then read back `/api/health`.
5. Point the Slack App Request URL at `/api/slack/events`, complete URL verification, and subscribe only to message events required by the selected conversation types.
6. Send one mention in an authorized test channel. Independently verify QStash acceptance, Multica Issue/comment persistence, reaction identity, Agent execution, and the final reply in the original thread.
7. Confirm that a blocked channel or sender produces no QStash or Multica side effect.

Configuration, deployment readiness, and HTTP 200 each prove only their own stage; none replaces end-to-end acceptance.

### Cloudflare Workers

Use `pnpm dev:cf` for local development, `pnpm build:cf` for an offline deployment build, and `pnpm deploy:cf` to publish after configuring your account and Secrets. See [Cloudflare configuration](docs/CONFIGURATION_EN.md#cloudflare-workers) for the complete setup. Workers hosts the Relay only; QStash, Upstash Redis, and the private Multica Runtime remain required.

## Local reply adapter

```bash
python3 scripts/slack-reply.py --help
```

The adapter reads route and `replyContext` data from the source Issue/comment, reads the fixed `displayName` and binding IDs from private JSON, and sends Block Kit messages with `SLACK_USER_TOKEN`. The Agent writes only the body; code appends attribution, model, and Fast labels.

Private JSON, Runtime Skills, and the Agent prompt do not belong in this repository. Editing a local prompt file alone does not change the Multica Agent. Synchronize it explicitly with `multica agent update --instructions`, then read back the same Agent ID.

## Validation

```bash
pnpm test   # Vitest + Python unittest
pnpm lint   # TypeScript typecheck
```

Tests cover signatures, admission, QStash projection, all 130 paginated non-mentions, initial nearby discussion, cache loss and out-of-order recovery, failed writes that do not advance the mention boundary, v4/v5 parsing, attachment references, footers, and uncertain-result/concurrency boundaries of the local delivery ledger. Worker changes also run `pnpm build:cf` to validate the deployment bundle.

Offline tests prove code contracts. They do not prove a real deployment, Agent execution, or a user-visible Slack reply. Release verification must exercise each stage in an authorized test channel.

## Security and privacy

- Credentials are supplied only through the deployment platform's secret store or the private Runtime environment.
- Raw Slack attachment objects never enter QStash.
- Logs contain digests, counts, timings, and stable error codes rather than message text, names, attachment contents, or tokens.
- Redis and QStash process selected Slack text; configure access and retention according to message sensitivity.
- Private prompts, persona material, Skills, and reply-adapter configuration must not be committed to the public repository.
