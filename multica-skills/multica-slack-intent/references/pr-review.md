# PR Review 与复审

PR 链接加 mention/cc 通常是 Review 请求；修改后再次 mention 或“再帮 A 一下”通常是复审。它们属于工程审查，区别于征求部署者的私人态度或业务决定。

主 Prompt 已常设授权协作写回时，任何已准入真人都可以发起这类请求；完成审查后默认直接写回目标 PR，无需部署者逐次批准。明确只读或不写回的请求优先。Skill 本身不向没有授权的部署新增权限。

## 审查与写回

1. 使用 `moe-pr-review`，按目标仓库规则读取需求、当前 head、变更、已有讨论和 CI。复审核对新增变更与历史问题，保持结论绑定当前 head。
2. 完整审查后，没有未解决的 P0–P2 或影响结论的未决问题，且符合审查 Skill 和仓库批准条件时，提交 **Approve**；只有 P3 可保留非阻断建议并批准。存在已确认阻塞问题时提交 **Request changes**；审查不完整或证据不足以给出整体结论时提交 **Comment**，说明具体缺口。
3. 按当前审查 Skill 区分真实阻塞与覆盖限制。只报告已核实的问题；“没运行某项测试”本身不自动成为新的阻塞条件。
4. 通过 `moe-github-workflow` 发布必要行内评论与整体结论。发送前重核 head；变化时先审新增内容。写后回读 Review state、commit_id 和内容；结果未知先查现状，避免重复发布。
5. 派给 Code Reviewer 审查时，派单里写明完成标准：交回前按第 2 步提交 Approve 或 Request changes 并回读；只有审查不完整时才提交 Comment，并写明缺口。对方只交回 Comment 而结论已足够时，视为未完成。
6. 使用最终回复 Skill 把审查结论与真实 Review 链接发回原线程。账号为 PR 作者等平台限制按实际结果说明，保持平台权限边界。

这项常设授权只覆盖该 PR 的审查写回；合并、auto-merge、部署、发布等特殊操作按主 Prompt 的 owner 授权规则处理。发起人请求 Approve 时仍先完成审查，由证据决定结论。
